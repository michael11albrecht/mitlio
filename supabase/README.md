# supabase/

Backend for mitlio (ADR-06): Postgres + RLS. Plan: `docs/IMPLEMENTATION_PLAN.md` §2.4 (data model), §8 (security).

Staging is deployed by CI (see "Deploy to staging"); no hosted project is linked locally. `project_id` in `config.toml` only names the local Docker stack.
Never run `supabase link` / `supabase db push` from an agent; deploys are an owner step.

## Layout

| Path | What |
|---|---|
| `config.toml` | Minimal local stack: db, auth (anonymous sign-ins on), rest, realtime. Storage, edge runtime, studio, inbucket, analytics are off. |
| `migrations/0001_core.sql` | Server schema mirroring the client Drift schema v2, sync columns, RLS. Merged migrations are append-only. |
| `types/database.ts` | Generated by `supabase gen types typescript --local` (`make db-types`). CI regenerates it and fails on any diff; commit the regenerated file with every migration. |
| `../tool/gen_db_contract.dart` | Reads `types/database.ts`, emits `app/lib/features/sync/data/db_contract.g.dart` (table/column names + coarse types). `app/test/db/db_contract_test.dart` checks the Drift schema is a subset of it. Differences: server-only `server_seq` columns and the server-only `group_memberships` / `group_invites` tables. |
| `migrations/0005_fuel_prices.sql` | `fuel_price_cache` (public read, service-role write), `rate_limits`, pg_cron jobs. Contract: `../docs/fuel-prices-api.md`. |
| `migrations/0006_fx_rates.sql` | `fx_rates` (public read, service-role write), pg_cron jobs. Contract: `../docs/fx-rates-api.md`. |
| `migrations/0008_delete_my_data.sql` | `delete_my_data()` RPC: removes the caller's memberships, unlinks their members, deletes their auth user; shared group data stays (`docs/data-deletion.md`). |
| `migrations/0007_expense_revisions.sql` | `expense_revisions` (member read, trigger-written snapshots before each expense change, newest 50 kept). Client twin: Drift schema v3. |
| `migrations/0009_join_hardening.sql` | `join_group` per-user rate limit (10/hour, SQLSTATE `P0429` `rate_limited`) and `group_join_audit` (member read, written only by `join_group`). |
| `migrations/0010_people_accounts.sql` | ADR-24: `group_memberships.role` (owner/member, trigger-enforced), owner-only `create_invite` (non-expiring, revokes other links) and `revoke_invite`, `connect_member`, `remove_membership`, `delete_my_data` hands ownership on. |
| `migrations/0014_inactive_accounts_cleanup.sql` | Retention for sync (#188): `delete_account_data(uid)` (internal, the one deletion path; `delete_my_data` now delegates to it) and the daily cron job `inactive-accounts-cleanup` (`cleanup_inactive_accounts()`): anonymous accounts inactive for 13 months, then groups with no linked account (with all rows). Activity signal in `docs/retention.md`. |
| `migrations/0015_push_notifications.sql` | P6b-T02 (ADR-13): `device_tokens` (own rows readable, written by `register_device_token` / `unregister_device_token`), `notification_prefs` (own rows), `notification_outbox` (no client grant, no policy). |
| `migrations/0016_notification_triggers.sql` | P6b-T03: writes of expenses (deferred to commit), settlements and members queue `notification_outbox` rows, only for user-visible changes by a signed-in actor, idempotent via `dedupe_key`. Pure recipient/coalesce/message logic: `functions/_shared/notify.ts`. |
| `migrations/0017_notify_claim_and_cron.sql` | P6b-T05: `claim_notification_outbox` (`FOR UPDATE SKIP LOCKED`), `retry_notification_outbox` (backoff, max attempts), `invoke_notify` + pg_cron `notify-outbox` every minute, outbox cleanup after 7 days. Edge Function: `functions/notify/`. |
| `migrations/0012_app_config.sql` | `app_config` (min_supported_version per platform, ADR-27 §2.3): the one anon-readable app table (the gate runs before sign-in), no client writes, owner edits it in the SQL editor. `join_group`'s `P0429` now carries `hint = 'retry_after_seconds=<n>'`. |
| `functions/` | Edge Functions (Deno 2.1.4). `fuel-prices/`, `fx-rates/` + pure logic in `_shared/`; `tests/coverage_gate.sh` (unit, >= 90 %) and `tests/run_integration.sh` (`functions serve` + provider stub). CI only; never `functions deploy` from an agent. |
| `functions/route-distance/` | P9-T08: start/destination text to coordinates and driving distance via openrouteservice (primary) or Geoapify (fallback), no migration (reuses `consume_rate_limit`). Contract: `../docs/route-distance-api.md`. |
| `tests/database/*.sql` | pgTAP: `rls_policies.sql` (per-table matrix), `rls_bootstrap.sql`, `rls_coverage.sql` (every table has RLS and tests), `schema_invariants.sql`. |

## Run locally (needs Docker)

CLI: **v2.70.0** (pinned in `.github/workflows/db.yml`; install the same version, e.g. a release tarball from
<https://github.com/supabase/cli/releases/tag/v2.70.0>).

```sh
make db-up      # supabase start
make db-reset   # re-apply migrations from scratch
make db-test    # supabase test db (pgTAP)
make db-lint    # squawk on migrations (no Docker; needs node)
make help       # without Docker the Docker targets print "needs Docker" and exit 1
```

## What CI does

`.github/workflows/db.yml` runs on PRs touching `supabase/**`: squawk, `supabase start`,
`supabase db reset`, `supabase test db`. It is the only place these run for agents.

## Rules for new tables

- Enable RLS, grant `select, insert, update` to `authenticated` only (no `anon`, no `delete`: soft delete via `deleted_at`).
- Add the table to the registry in `tests/database/rls_coverage.sql` and to `TABLES` coverage in `rls_policies.sql`, or CI fails.
- Server-only data never mirrors client-only secrets: **no IBAN columns** (`members.iban_hint` is a masked hint, max 14 chars).

## Deploy to staging

`.github/workflows/deploy-dev.yml` (P8-T03, backend half) runs on every push to `main` that touches
`supabase/**`, and on manual `workflow_dispatch` (Actions tab, branch `main`). It uses the GitHub environment
`staging` (secrets `SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF`, `SUPABASE_DB_PASSWORD`) and runs:

1. `supabase link`, then `supabase db push --dry-run` (printed to the job summary), then `supabase db push --yes`.
   No `--include-all`: out-of-order migrations fail instead of being applied silently.
2. `supabase functions deploy <name> --use-api` for every directory in `functions/` with an `index.ts`
   (`fuel-prices`, `fx-rates`, `route-distance`). `_shared/` and `tests/` are not functions. `verify_jwt` stays at its default
   (on); clients and pg_cron call with the anon key as bearer token.
3. Smoke check: `supabase migration list` must show every local migration applied remotely, else the job fails.

The first run applies migrations 0001..latest to the empty project. The PR gate (`db.yml`) has already
validated them; the deploy job does not re-run tests. Deploys are serialized (`concurrency: deploy-staging`).
The access token expires after 90 days: rotate it in the `staging` environment before then.

### Owner steps (one time, not automated)

- Extensions: migrations run `create extension if not exists` for `pgcrypto` (schema `extensions`),
  `pg_cron` (schema `pg_catalog`) and `pg_net` (schema `extensions`). All are available on the Free plan. If the
  first push fails on one of them, enable it in Dashboard > Database > Extensions and re-run the workflow.
- Auth: enable anonymous sign-ins (Dashboard > Authentication > Sign In / Providers), as in `config.toml`.
- Edge Function secrets, set once with `supabase secrets set NAME=value --project-ref <ref>` (never in CI):

  | Secret | Function | Purpose |
  |---|---|---|
  | `TANKERKOENIG_API_KEY` | fuel-prices | Tankerkoenig key; optional, without it fuel prices are unavailable |
  | `FUEL_WARM_TOKEN` | fuel-prices | shared secret for the pg_cron cache warm-up |
  | `FUEL_RATE_LIMIT_SALT` | fuel-prices | salt for hashed rate-limit keys |
  | `FUEL_ALLOWED_ORIGINS` | fuel-prices | CORS origins; set by `deploy-dev.yml` on every deploy (override via the variable `FUEL_ALLOWED_ORIGINS`), not by hand. Prod needs the same step |
  | `TANKERKOENIG_BASE_URL`, `OIL_BULLETIN_URL` | fuel-prices | optional overrides |
  | `FX_WARM_TOKEN` | fx-rates | shared secret for the pg_cron warm-up |
  | `FX_RATE_LIMIT_SALT` | fx-rates | salt for hashed rate-limit keys |
  | `FX_ALLOWED_ORIGINS` | fx-rates | CORS origins |
  | `FX_PROVIDER_URL` | fx-rates | optional override |
  | `ORS_API_KEY` | route-distance | openrouteservice key: sign up for free at <https://openrouteservice.org/dev/#/signup>, create a token, `supabase secrets set ORS_API_KEY=<token> --project-ref <ref>`. Without any provider key the feature answers 503 and the app falls back to manual km |
  | `GEOAPIFY_API_KEY` | route-distance | optional fallback provider key (<https://www.geoapify.com/>) |
  | `ROUTE_PROVIDER` | route-distance | optional order, default `openrouteservice,geoapify`; e.g. `geoapify` to switch without an app update |
  | `ROUTE_RATE_LIMIT_SALT`, `ROUTE_ALLOWED_ORIGINS` | route-distance | salt for hashed rate-limit keys, CORS origins |
  | `ROUTE_SUGGEST_PER_MIN`, `ROUTE_DISTANCE_PER_MIN`, `ROUTE_SUGGEST_DAILY`, `ROUTE_DISTANCE_DAILY` | route-distance | optional limits (defaults 30/10 per user and minute, 1000/1500 global per UTC day: keep the daily ones below the provider quota) |

  `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are injected by the platform.
- pg_cron warm-up jobs read Vault secrets and silently do nothing until they exist: `fuel_prices_url`,
  `fuel_prices_anon_key`, `fuel_prices_warm_token` (same value as `FUEL_WARM_TOKEN`), and `fx_rates_url`,
  `fx_rates_anon_key`, `fx_rates_warm_token` (same value as `FX_WARM_TOKEN`). Create them in the SQL editor with
  `select vault.create_secret('<value>', '<name>');`.
- The `notify` push job (`invoke_notify`, every minute) works the same way: Vault secrets `notify_url`
  (`https://<ref>.supabase.co/functions/v1/notify`), `notify_anon_key`, `notify_token` (same value as the
  function secret `NOTIFY_TOKEN`). The function itself needs the secrets `NOTIFY_TOKEN`, `FCM_ENDPOINT`
  (`https://fcm.googleapis.com/v1/projects/<firebase-project-id>/messages:send`) and `FCM_SERVICE_ACCOUNT`
  (service-account JSON, set with `supabase secrets set`, never committed). Optional: `NOTIFY_MAX_ATTEMPTS`
  (5), `NOTIFY_BATCH_SIZE` (200), `NOTIFY_CONCURRENCY` (10). Without FCM secrets it answers 503
  `fcm_not_configured` and leaves the outbox untouched. Each run logs one JSON line with counts only.

## Auth audit logs (#206, owner step per project)

Supabase Auth writes a row to `auth.audit_log_entries` for every token refresh and logout (user ID in the payload).
Nothing deletes these rows and they survive `delete from auth.users`, so they would outlive "delete all my data"
and the inactive-account cleanup (`docs/retention.md`). This is a hosted-project setting, not part of
`config.toml` (which is never pushed), so it is done in the dashboard for **every** project (staging and `mitlio-prod`):

1. Dashboard > Authentication > Configuration > Audit Logs: switch off storing audit logs in the database. Save.
   (The label may differ; it is the toggle behind `GOTRUE_AUDIT_LOG_DISABLE_POSTGRES`.)
2. Check in the SQL editor after one anonymous sign-in from the app; expected `0`:

```sql
select count(*) from auth.audit_log_entries where created_at > now() - interval '1 hour';
```

Events then only reach the platform log stream (1 day on Free, 7 days on Pro).
Also per project: Authentication > Rate Limits > anonymous sign-ins 10 per hour per IP; usage alerts for MAU and database size.
